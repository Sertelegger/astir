# #86 — failing timelines for the redesign

The claim/sighting design on this branch (96d3367) is **on hold for a
redesign** after four review rounds. Each round fixed the previous findings and
introduced new ones. The root problem: two signals that name no agent (a
`claude agents --json` sighting of "permission prompt" in a session, and the
`permission_prompt` Notification) have to be attributed to one of several
per-agent claims (PermissionRequest, which carries no `tool_use_id` and no
agent id).

These files are the acceptance tests for any redesign. They are not part of
the suite: `probes/` is outside tsconfig, biome and vitest. To run one, copy it
into `test/` of a worktree at the commit it targets. A `*-main*` file targets
main before #86 (07c3935); the others target 96d3367. The `verify/` files were
adapted to the `screen` field that 96d3367 introduced. Fixture paths inside a
few files point at the worktree they ran in, so fix those up.

- `verify/`: the round-3 verifier's replays of earlier probes (R1–R6 sweeps,
  F1/F3/F4, M19), the retraction case (`zzv-vr3-retract`, RY/RX), and a real
  Daemon `/healthz` probe. `mutate.py` is its mutation runner.
- `hunt/`: the round-3 adversarial hunt (S1–S7). `vr3-p86.test.ts` targets
  96d3367 and `vr3-p86-main.test.ts` targets 07c3935, with the same hooks.
- `skeptics/`: independent reproductions by the skeptics who upheld each
  finding.

Measured facts these timelines rely on (Claude Code 2.1.291/2.1.312):
PermissionRequest ~0.4 s after PreToolUse, dialog visible ~0.8 s, Notification
~6.2–6.6 s after PermissionRequest, Esc fires no hook, the listing reads
`waiting`/"permission prompt" while a Bash dialog is up and `idle` after Esc.
Claude also fires PermissionRequest with no dialog for background agents that
deny themselves (resume, fork, dontAsk/plan).

## Findings at 96d3367 (round 3)

### VR3-86-1 [bug] skeptic: upheld
retractYoungerBlocks checks the blocked agent's newest claim (dialogSince) for youth instead of the date of the block it retracts. When an agent re-claims while blocked (parallel ask), another agent's permission_prompt Notification can retract a real, announced, on-screen block: it sends `resolved` for the dialog still on screen and moves the alert to an agent whose dialog is only queued. Trigger: (a) the blocked agent fires a second PermissionRequest while blocked (the authors' own model, see test/claude-permission.test.ts:453 'A second ask while the first dialog is open (parallel tool calls)'), and (b) another agent claimed within about 1.4 s after the first claim.
REPRO: Probe probes/86/verify/zzv-vr3-retract.test.ts ('RY'), uses the real Registry and NotifyLoop. Steps: main pre+PermissionRequest @0; seen(500) landing @1.3 s; SUB pre+PermissionRequest @1.0 s; main PermissionRequest again @3 s; seen(5000) @5.3; pulse @6; Notification @6.4; pulse @7. Output: `RY @6 main blocked | sub tool-running`, `RY @6.4 main tool-running | sub blocked`, `RY sent ["blocked:main@6000","blocked:sub@7000","resolved:main@7000"]`. Main's dialog, open since 0.4 s and the one the Notification reports, gets a false `resolved`. In noticeOwner, main's claim 3 is under 5 s old, so the Notification goes to SUB (claim 1.0), and retractYoungerBlocks then retracts main because `now - a.dialogSince` (3.4 s) < 5 s, although main's block dates from its claim at 0.
FIX: In retractYoungerBlocks compare the block's own date: `if (a.dialogSince === null || now - a.stateSince >= NOTICE_MIN_AGE_MS) continue;`. A sighting-made block's stateSince is the claim it was dated from. Tried in a scratch worktree: test/claude-permission.test.ts and test/registry.test.ts pass 155/155. RY becomes `["blocked:main@6000","blocked:sub@7000"]` with no false resolved, which is the documented 'claims close together' limitation. Add a regression test for the RY sequence.

### VR3-86-2 [doc-false] skeptic: upheld
The comment on registry.ts retractYoungerBlocks says 'Only a sighting can have made such a block: a Notification blocks a claim only once it is old enough, and a younger claim is never one.' A block a Notification made (with no claim at all) is retracted once its agent re-claims. The same root cause as VR3-86-1 also contradicts 'as if it had never begun' (that block had been announced 7 s earlier).
REPRO: Same probe file, case 'RX': main pre + plain permission_prompt Notification @0 (no claim, so the Notification makes the block); SUB claims @3 s; main PermissionRequest @10 s while blocked; Notification @12 s. Output: `RX @0 main blocked permission_prompt stateSince 0 dialogSince null`, `RX @10 main blocked stateSince 0 dialogSince 10000 blocksBegun 1`, `RX @12 main tool-running null dialogHeldAt 12000 | sub blocked permission_prompt`, `RX sent ["blocked:main@5000","blocked:sub@13000","resolved:main@13000"]`.
FIX: The stateSince fix in VR3-86-1. With it, RX keeps main blocked (`RX sent ["blocked:main@5000","blocked:sub@13000"]`), and the comment becomes true.

### VR3-86-3 [doc-false] skeptic: upheld
hooks/README.md has two paragraphs headed '**The Notification names no agent.**'. The second is a stale copy saying a permission_prompt Notification 'goes to the agent with the newest claim … and to the main agent only when no agent holds a claim', with no 5 s minimum and no retraction. It contradicts the paragraph above it and the code (noticeOwner requires a claim at least NOTICE_MIN_AGE_MS = 5 s old).

Output: `DOCS lone young claim: main blocked permission_prompt | sub tool-running null dialogSince 3000`. An agent holds a claim, yet the Notification blocks main, not SUB.

### VR3-86-4 [coverage-gap] skeptic: n/a
7 of 33 mutants survive. Near-equivalent: N06 (the loop's retire() clears announcedAt on the next pulse anyway), N15 (a held timestamp from an earlier claim is always at or before the new claim, so max() ignores it), M02 (Claude's Notification never carries agent_id and Codex never has claims, so noticeOwner is null), M03 (a Claude Notification's agentType/parent/description are already null). REPRO: probes/86/verify/mutate.py, log in probes/86/verify/mutants.out. For example `N04 retract boundary >= -> >: SURVIVED [full22] | 567 passed (567)`, `N07 retract any reason: SURVIVED [full22] | 567 passed (567)`, `M05 noticeOwner: no blocked tie preference: SURVIVED [full22] | 567 passed (567)`.

### VR3-86-5 [nit] skeptic: n/a
counters.blocked (blocksBegun) keeps counting a block that retractYoungerBlocks takes back 'as if it had never begun', so one real dialog counts twice. blocksBegun's comment says it is 'Counted where every state change is made (`transition`)', but retractYoungerBlocks sets `a.state = "tool-running"` directly (registry.ts:851). No begun block is missed, so the counting conclusion holds.
REPRO: Real Daemon probe (zzv-vr3-healthz 'retracted'): `@5.3 main tool-running bg blocked blocksBegun 1`, `@6.4 main blocked bg tool-running blocksBegun 2`, `healthz.counters ... "blocked":2 blockedCount 1`.
FIX: Either decrement on retraction or reword both comments to say a retracted block stays counted and that retraction changes state outside transition().

### VR3-86-6 [nit] skeptic: n/a

The Esc entry's '(or `shell`, idle with a background shell running)' describes a path the README itself calls dead, since `claude agents --json` folds shell into busy; it works only if shell ever arrives (probe: `DOCS shell -> waiting`).

### F1-retract-keyed-on-refreshed-claim [regression] skeptic: upheld
retractYoungerBlocks (registry.ts:845) and noticeOwner (:870-875) judge a blocked agent by its newest claim (dialogSince), which a second PermissionRequest overwrites while the agent is blocked. The Notification for the dialog still on screen then goes to an older claim from another agent, and the real block is retracted. Result: a false 'resolved' while the dialog is up, plus a false alert, with reminders, for an agent whose dialog was approved long ago.
REPRO: Test 'VR3 S1 … parallel re-claim while A is on screen' in probes/86/hunt/vr3-p86.test.ts (real Registry + NotifyLoop, fake clock, polls every 5 s from 4 s). Timeline: SUB claims at 0 s, approved at 0.8 s, tool runs to 120 s. Main's PreToolUse + PermissionRequest A at 3 s, on screen 3.4–60 s; the sighting at 4 s blocks main. Main asks again (parallel B) at 8.5 s while blocked. A's Notification at 9.4 s. Main's PostToolUse at 61 s. B's Notification at 66.2 s. #86 sends ["blocked:main@8","blocked:a5cf41e52d9b8f355@10","resolved:main@10","blocked:a5cf41e52d9b8f355@70","resolved:a5cf41e52d9b8f355@95"]: main is resolved at 10 s while A is on screen and never alerted again; SUB, whose dialog was approved at 0.8 s, is alerted and reminded. 07c3935 with the same hooks (vr3-p86-main.test.ts 'S1') sends ["blocked:main@15","resolved:main@61","blocked:main@72"]. Without the re-claim the control is clean: ["blocked:main@8","resolved:main@61"]. Precondition (not measured live): a blocked agent asks again at least ~1.4 s after its first dialog showed, from parallel or streamed tool calls. The suite models this itself at test/claude-permission.test.ts:453-470 and :1110, a second ask 3 s into an open dialog. It also needs another agent's claim at least 5 s old and not yet lapsed (made within 10 s, or held). The surviving mutant B5 shows nothing in the suite pins which timestamp is used. The 66 s tail of this story is F2's mechanism.
FIX: For a blocked agent, match against the start of its block, not its newest claim: in noticeOwner use since = isBlocked ? Math.min(stateSince, dialogSince) : dialogSince (and the same in the 'best' comparison), and in retractYoungerBlocks test now - a.stateSince. I probed this combination: test/claude-permission.test.ts still passes 115/115, and S1 becomes ["blocked:main@8","resolved:main@61",…] with no false resolve or SUB alert at 10 s. Changing only retract to stateSince (B5) removes the false resolve but SUB is still falsely blocked at 10 s. Add S1 as a regression test.

### F2-held-claim-steals-claim-wiped-dialog [regression] skeptic: upheld
Held claims (dialogHeldAt) keep another agent's claim open for as long as a standing block keeps being seen, whether that claim was approved long ago or denied by Claude itself. When the standing block ends through its agent's own PostToolUse, transition() wipes that agent's claim, even though its parallel second dialog is now on screen. The held claim then becomes the newest: the next sighting blocks it (a false alert, dated from a long-gone claim, so it skips the dwell), and it takes the second dialog's Notification. When that agent next makes progress it is resolved, and the real dialog is never blocked or alerted. Main even decays to idle with the dialog on screen.
REPRO: Tests 'VR3 S2 … (dead SUB2 claim: true)' and 'VR3 S2c' in probes/86/hunt/vr3-p86.test.ts, with vr3-p86-main.test.ts using identical hooks on 07c3935. S2: main asks for A at 0 s and parallel B at 0.3 s, seen at 1 s. SUB2's background ask at 3 s is denied by Claude itself, and SUB2 next acts at 45 s. A's Notification at 6.4 s. A is approved at 20 s and its PostToolUse comes at 21 s; B is on screen from 20 s. B's Notification at 26.2 s. #86 sends ["blocked:main@6","resolved:main@21","blocked:b6df52f63e0c9a466@22","resolved:b6df52f63e0c9a466@45"]; main is never blocked on B, through 180 s. Without SUB2: ["blocked:main@6","resolved:main@21","blocked:main@32",…]. 07c3935 with SUB2: ["blocked:main@12","resolved:main@21","blocked:main@32","blocked:main@92","blocked:main@152"] main=blocked. S2c is the common variant: SUB was approved at 0.5 s and its tool runs 5 min; main asks A at 1 s and B at 1.3 s. #86 sends ["blocked:main@7","resolved:main@61","blocked:a5cf41e52d9b8f355@66","…@126","…@186","…@246","resolved:a5cf41e52d9b8f355@300"], and at 400 s main=idle with B on screen. 07c3935 sends ["blocked:main@13","resolved:main@61","blocked:main@72",…,"blocked:main@372"] main=blocked. Root cause confirmed: with holds disabled (mutant A1 or A2), both timelines match 07c3935. Assumptions: (1) two asks from one agent can be pending at once (concurrency-safe parallel tools; the suite assumes this, not measured); (2) Claude sends permission_prompt once per dialog. If it re-sends every 6 s, B is alerted late under the wrong agent instead of lost, but the false SUB/SUB2 alerts and reminders, and main=idle at 400 s in S2c, still stand.
FIX: Do not let a block that ends through the agent's own post_tool wipe a claim that is still outstanding. Count asks against finished tools per agent (permission_request vs post_tool/tool_failed). While asks outstanding exceed finished tools, keep dialogSince open, held from the latest sighting, so the agent's own dialog stays the newest claim. Separately, consider ending holds that a standing block made once that block ends with the session still 'busy'.

### F3-changelog-real-prompt-never-dropped [doc-false] skeptic: upheld
The CHANGELOG Known-limitations entry 'A request Claude refuses on its own can be taken for a real prompt' says: 'The real prompt is never dropped: astir keeps it while the session list keeps showing a prompt, and alerts it as soon as the background agent's block ends.' The settleFromListing doc comment makes the same claim ('Late, never lost'). In F2's S2, which is exactly the documented case, the background agent's block ends at 45 s and the real prompt is never alerted.
REPRO: S2 dead=true in probes/86/hunt/vr3-p86.test.ts: ["blocked:main@6","resolved:main@21","blocked:b6df52f63e0c9a466@22","resolved:b6df52f63e0c9a466@45"]. The listing shows a permission prompt until 200 s and main is never blocked. A sighting cannot block B, because its claim was wiped at 21 s. So 'alerts it as soon as the background agent's block ends' is false even if Claude re-sends Notifications.
FIX: Fix F2, or narrow the sentence to prompts whose own claim is still open, and add a limitation for a second parallel prompt from the same agent.

### F4-session-wide-decay-skip [regression] skeptic: upheld
The new tick() skip (registry.ts:934-938) turns off idle and stall decay for every agent in a session while any agent there is blocked, of any reason, acknowledged or not. An agent that really stopped shows as working, and banks working time (G4), for the whole block. If nothing ever ends that block, it never decays. On 07c3935 it went idle after 30 s.
REPRO: VR3 S4 tests in probes/86/hunt/vr3-p86.test.ts against vr3-p86-main.test.ts. S4: SUB's last event is PostToolUse at 5 s, with no SubagentStop. SUB2's dialog is seen and blocked from 10 s to 600 s, and the listing reads waiting. #86: SUB stays 'thinking' at 600 s, then goes idle with activeMs=610900. 07c3935: SUB is idle by 35 s with activeMs=36900. S4b: agent_needs_input on main, then Esc; this block is not ended by the listing. #86 at 1 h: main=blocked SUB=thinking. 07c3935: SUB=idle. S4c, Codex: one agent blocked, a sibling silent for 16 min with status null. #86: thinking. 07c3935: idle. Precondition: a lost terminal hook, or any block nothing ends, such as the documented masked-session and Esc-after-Notification cases. Mutants D2 and D3 survive, so the scope of the skip is not tested.
FIX: Limit the skip to what it was added for: the parent of a blocked subagent (parentId chain, or agents whose tool is Agent/Task), or at least to permission_prompt blocks the listing can end. Keep the stalledAfterMs backstop running in any case.

### F5-r4-discards-come-look-notification [bug] skeptic: n/a
R4 (registry.ts:744-751) returns early, so an agent_needs_input or worker_permission_prompt Notification that arrives during a permission block is never recorded anywhere. If that block then ends within the dwell, for example Esc read as idle, nothing is ever sent for a kind that BLOCKING_NOTIFICATIONS defines as 'come look'. 07c3935 alerted it.
REPRO: 'VR3 S5 … agent_needs_input during an unannounced permission block, then Esc' in probes/86/hunt/vr3-p86.test.ts. Claim at 0 s, seen at 1 s. agent_needs_input at 3 s returns becameBlocked=undefined, and the reason stays permission_prompt. A poll begun at 4 s reads idle; pulses run to 120 s. #86 sends []. 07c3935 (vr3-p86-main.test.ts 'S5') sends ["blocked:main@8","blocked:main@68"] main=blocked. Not stopping blocking after Esc once announced is documented as intended in the CHANGELOG. The defect is the never-alerted path. Caveat: how long agent_needs_input stays relevant is unmeasured (registry.ts:139 says as much).
FIX: Instead of dropping it, remember the pending non-permission reason, for example in a field. When the permission block ends through the listing, move the agent into a block for that reason, dated from its arrival. Or at least send it once.

### F6-blocksbegun-counts-retracted [nit] skeptic: n/a
retractYoungerBlocks sets state directly without going through transition(), and does not undo this.blocks++. A block 'taken back as if it had never begun' therefore still adds to /healthz counters.blocked.
REPRO: 'VR3 S7' in probes/86/hunt/vr3-p86.test.ts: one real dialog. The sighting gives the younger SUB2 claim a block, and the Notification retracts it. Log: 'blocksBegun before=1 after=2 blocked now=1'.
FIX: Decrement this.blocks in retractYoungerBlocks, or document that the counter includes blocks that were taken back.

### F7-mutation-survivors [coverage-gap] skeptic: n/a
11 of 25 mutants of the five new rules survive test/claude-permission.test.ts. 9 are not equivalent, so the suite does not pin them.
REPRO: Run python3 probes/86/hunt/mutate.py test/claude-permission.test.ts in a 96d3367 worktree. Each survivor passes 115/115. Not equivalent: B5 retract uses stateSince (this is F1). B9 retract any blockedReason (would retract a re-claimed agent_needs_input block). D2 skip only for permission blocks, and D3 skip only for unacknowledged blocks (F4). B8 noticeOwner tie-break removed (a same-ms open claim can double-block one dialog). B7 retract boundary >= to > and C2 standing filter >= to > (inconsistent at exactly 5000 ms or at dialogStart; 1 ms boundary). E3 and E4 R4 sub-conditions (edge only, reason label). Equivalent: A6, because a new claim keeping its old dialogHeldAt changes nothing (holds always come before the new claim, so max() picks the claim). E2, because dropping 'blocked &&' changes nothing (blockedReason is null whenever the agent is not blocked).
FIX: Add the S1 and S2c timelines, an acknowledged-block plus decay case, a non-permission block plus decay case, and exact-5000 ms boundary cases for retract and noticeOwner.
